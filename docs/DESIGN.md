# BreedingLog 設計文件

## 1. 專案概述

BreedingLog 是一個以「關係經營」為核心的 Minecraft 動物養殖插件，目標是把原本簡單的「餵食即繁殖」機制，轉成更具策略性與長期回饋的牧場系統。

核心思想分成三條主線：

- 個體關係線：每隻動物都有好感度、性別、孕期與成長狀態。
- 玩家牧場線：玩家透過收穫、擊殺與經營累積經驗，提升牧場等級與解鎖掉落表。
- 繁殖與育幼線：成熟動物必須符合配對條件，才可繁殖；母體會進入孕期，產下蛋，拾取後生成幼崽。

這個插件預計兼容 Paper / Spigot / Folia，並依賴 CraftEngine 提供自訂物品與掉落系統。

---

## 2. 設計目標

### 2.1 主要目標

1. 提供可持續的動物經營玩法，而非單純的繁殖模組。
2. 讓牧場管理與個體關係同時存在，形成雙軸玩家回饋。
3. 兼容多個伺服器核心，尤其是 Folia 的區域調度模型。
4. 讓所有內容可配置，方便伺服器管理員調整難度與掉落表。
5. 讓 CraftEngine 物品整合變成可擴充的能力，而不是硬編碼。

### 2.2 非目標

- 不設計成完全獨立的資料庫型牧場管理系統。
- 不追求超高抽象的框架層，專注於實際場景穩定性與可維護性。
- 不打算支援所有魔改生物；先以原版可繁殖動物為中心。

---

## 3. 系統設計原則

### 3.1 低耦合

模組之間以清楚責責任邊界為準：

- `scheduler` 負責核心時序與執行緒切換。
- `data` 負責持久化/標記資料。
- `listener` 負責事件接收。
- `command` 負責玩家互動。
- `config` 負責配置讀取。
- `craftengine` / `i18n` 做擴充整合。

### 3.2 伺服器核心抽象

由於 Paper 與 Folia 對事件與定時任務的處理模式不同，專案採用 `SchedulerAdapter` 抽象層：

- `PaperSchedulerAdapter`：使用 `Bukkit.getScheduler()`。
- `FoliaSchedulerAdapter`：使用 `Entity#getScheduler()` / `World#getRegionScheduler()` / `Bukkit#getGlobalRegionScheduler()`。

如此可避免業務邏輯直接依賴核心差異。

### 3.3 配置優先

所有數值應以配置為主，例如：

- 好感度上下限與衰減值
- 繁殖條件門檻
- 孕期長度
- 牧場經驗公式
- 掉落表分段

這能降低版本迭代時的硬編碼風險。

### 4.1 核心類別

```text
BreedingLogPlugin
├── scheduler/
│   ├── SchedulerAdapter.java
│   ├── PaperSchedulerAdapter.java
│   └── FoliaSchedulerAdapter.java
├── data/
│   └── PdcKeys.java
├── listener/
├── command/
├── config/
├── animal/
├── craftengine/
├── i18n/
└── resources/
    ├── plugin.yml
    ├── config.yml
    └── lang/
```

### 4.2 啟動流程

1. `BreedingLogPlugin.onEnable()` 呼叫 `saveDefaultConfig()`。
2. 建立 `PdcKeys`，用於封裝 PersistentDataContainer 的 key。
3. 判斷伺服器是否為 Folia，選擇對應 `SchedulerAdapter`。
4. 啟動後續模組，例如：
   - 事件監聽器註冊
   - 指令註冊
   - 配置載入與語系初始化
   - 動物註冊表建立

## 5. 核心功能設計

## 5.1 動物個體狀態

每隻動物都會被視為一個「個體」，並保留以下狀態：

- `ownerUuid`：牧場擁有者 UUID（若已領養）
- `gender`：MALE / FEMALE
- `affection`：好感度，範圍 0~100
- `ageStage`：BABY / ADULT / SENIOR（如需擴充）
- `pregnant`：是否懷孕
- `pregnancyProgress`：孕期進度
- `pregnancyDuration`：孕期總長
- `adopted`：是否已被領養
- `speciesType` / `entityType`：動物種類
- `lastFed` / `lastTouched`：與互動冷卻相關資訊

這些資料可存放於：

- `PersistentDataContainer`（優先，適合每隻實體的輕量資料）
- 玩家或全域快取（若後續需要高階查詢）
- 可選 SQLite（長期備份或跨重啟恢復）

### 5.2 性別系統

性別的設計目的是避免無條件繁殖，並使玩法更像「動物管理」而非單純刷幼崽。

規則：

- 同類動物必須一公一母。
- 繁殖只能在成年個體之間進行。
- 需要符合好感度門檻（預設 60）。
- 不能處在懷孕或冷卻狀態。

若伺服器需要管理員修正，可提供 `/bbreeding setgender`。

### 5.3 好感度系統

好感度是「個體關係」核心值，直接影響是否能繁殖。

初始值：50

互動行為：

- 撫摸：+5
- 攻擊：-10
- 頻繁收穫：-3
- 每日自動衰減：-1
- 下限：50

設計目的：

- 讓動物不只是可繁殖的資源，而是需要經營的人際關係。
- 確保玩家需要花時間維持好感度。
- 避免「一旦好感度高就無限制繁殖」造成平衡問題。

### 5.4 牧場等級系統

牧場等級是全局系統，用來衡量玩家多年的牧場經營成果。玩家獲得經驗來源包括：

- 收穫動物產物
- 擊殺動物
- 進階養殖活動（如繁殖、育幼）

規則：

- 經驗累積至等級門檻後解鎖收益與功能
- 主要影響物品掉落機率與稀有品級
- 可透過配置文本設計「等級曲線」

設計上應與「牧場任務」或「進度表」分離，保持單一責任：

- 牧場等級：數值與解鎖邏輯
- 掉落策略：位於 `drops.yml` 的分段表

### 5.5 繁殖與孕期

繁殖流程設計如下：

1. 玩家或系統判定兩隻動物符合條件。
2. 確認同種、異性、成年、好感度達標、非懷孕。
3. 隨機決定是否成功（可保留低風險配置化）。
4. 母體進入孕期，計算預設孕期長度。
5. 到達孕期後，母體產下「BreedingLog 蛋」。
6. 玩家拾取該蛋並右鍵使用，生成幼崽。
7. 幼崽隨機產生性別與出生狀態。

此設計符合「牧場經營」主軸：需要管理育成時間，而非直接刷出生。

### 5.6 領養系統

野外動物可以被領養，視為加入玩家牧場。

領養方式：

- 空手 + Shift + 右鍵點擊動物
- 若符合可領養條件，分配：
  - `ownerUuid`
  - `gender`（隨機）
  - 初始好感度
  - 設定物種標記

動物被領養後，應由系統進行以下處理：

- 避免其他玩家誤觸
- 保留可追踪的個體狀態
- 保持與牧場等級相關的行為邏輯一致

### 5.7 掉落與收穫系統

此插件將收穫系統切成幾個層級：

- 通用收穫：適用於一般動物產物
- 工具收穫：刷子、剪刀等專用工具
- 被動掉落：糞便、牛奶、蘑菇湯等

所有掉落都由配置表控制，支援：

- 分等級掉落
- CE 自訂物品
- 機率與數量調整
- 依牧場等級變化

這樣可讓伺服器管理員更容易微調平衡，而不需要修改 Java 代碼。

## 6. 數據設計

### 6.1 PersistentDataContainer (PDC)

PDC 是最適合保存個體狀態的資料層，基本理由：

- 對應每一個實體實例
- 不需要額外資料表
- 透過標準 Bukkit API 可直接讀寫

建議使用 `PdcKeys` 封裝鍵值，避免字串散落各處。

### 6.2 Player/Global State

玩家狀態可保存在快取中，內容包括：

- 牧場等級
- 經驗值
- 語言設定
- 最近切換的顯示狀態

這些狀態通常不需要大量儲存，且可以在玩家登入時重建。

### 6.3 語言系統

多語言設計採用 `lang/<code>.yml` 的方式，支援：

- zh_TW（官方）
- en_US（官方）
- zh_CN（社群）

各語言檔負責：

- 命令回應
- 事件提示
- 動物互動訊息
- 錯誤訊息

目標是讓插件內容與 UI 邏輯脫離 Java 程式碼。

## 7. 模組設計

### 7.1 `command`

命令模組設計要符合最小命令集合：

- `/bbreeding info`
- `/bbreeding toggle`
- `/bbreeding transfer`
- `/bbreeding gender`
- `/bbreeding lang`
- `/bbreeding reload`
- `/bbreeding setgender`
- `/bbreeding givece`

責任：

- 解析參數
- 檢查權限
- 呼叫對應服務
- 回傳可讀的訊息

### 7.2 `listener`

監聽器應以事件驅動為中心：

- 玩家互動事件
- 動物受傷事件
- 動物收穫事件
- 動物繁殖事件
- 實體生成事件
- 物品撿起事件

重點：

- 盡量只做判斷與協調，不做大量業務邏輯。
- 事件處理的長計算要轉交 service 或 manager 類別。

### 7.3 `config`

配置類應包含：

- 成功讀取與驗證
- 預設值回退
- 熱重載支援

建議將配置拆成：

- `config.yml`：核心玩法配置
- `drops.yml`：掉落表
- `lang/*.yml`：語言檔

### 7.4 `animal`

這部分是核心業務的中樞，負責：

- 動物類型註冊
- 觸發繁殖條件檢查
- 管理性別、好感度、孕期
- 應用屬性與狀態更新

這層應保持「業務邏輯與執行細節分離」。

### 7.5 `craftengine`

CraftEngine 整合預計用於：

- 自訂物品生成
- 蛋類特殊物品
- 稀有掉落物
- 自訂資源包與紋理

設計上建議做一層適配器，而不是直接在多個模組中寫死 CE API。

### 7.6 `scheduler`

目前已建立了基本接口：

- `runAtEntity(Entity, Runnable)`
- `runAtLocation(Location, Runnable)`
- `runDelayedAtEntity(Entity, Runnable, long)`
- `runGlobal(Runnable)`

這層不可被業務邏輯直接繞過，否則 Folia 兼容性很快失控。

## 8. 資料流程

### 8.1 領養流程

```text
玩家右鍵動物
→ 檢查是否為野生可領養動物
→ 檢查是否為空手與 Shift
→ 隨機分配性別
→ 寫入 ownerUuid / gender / affection
→ 發送領養成功提示
```

### 8.2 繁殖流程

```text
動物互動觸發繁殖判定
→ 檢查同種 / 異性 / 成年 / 好感度 >= 60
→ 檢查是否懷孕中、是否冷卻中
→ 生成胎期資訊
→ 母體進入孕期
→ 計時器到期後產下 CE 蛋
```

### 8.3 收穫流程

```text
動物產物生成/收穫事件
→ 判斷是否為可收穫物
→ 依玩家牧場等級查掉落表
→ 計算經驗與好感度變化
→ 生成物品或加成效果
```

## 9. 伺服器兼容性設計

### 9.1 Paper

適合作為主開發環境，功能最完整，API 最穩定。

### 9.2 Spigot

目標保證大多數功能可在 Spigot 上運行，但需要注意：

- 某些 Folia 專屬 API 不可依賴
- 跨區調度細節需抽象，避免直接使用 Folia API

### 9.3 Folia

Folia 是主要設計重點之一，跨區任務調度需要：

- 以實體或區域為單位執行任務
- 保持世界資源操作在正確區塊/區域中
- 不讓全域任務對整個伺服器造成壓力

因此，所有與時間、狀態更新相關的操作都必須經過 `SchedulerAdapter`。

## 12. 風險與限制

### 12.1 風險一：Folia API 差異

解法：所有關鍵調度都由 `SchedulerAdapter` 寫死，不允許直接在業務層使用 `BukkitScheduler` 或 `World` 的 Folia API。

### 12.2 風險二：資料持久化不一致

解法：所有個體資料以 PDC 為主，必要時使用快取與配置驗證，避免資料結構過度複雜。

### 12.3 風險三：掉落表過於複雜

解法：先實作分層掉落表，後續再補高階邏輯；不要一開始就做高度自定義腳本。

### 12.4 風險四：動物種類差異過大

解法：先實作共通動物能力，再對特殊生物（熊貓、狐狸、蜜蜂等）加特例分支。

## 15. 結論

BreedingLog 的設計重點，不是單純做一個「動物繁殖插件」，而是做一個具備牧場經營感、長期成長感與個體管理感的生態模組。

它以「個體關係」與「牧場等級」雙軸設計，並透過 Paper / Folia 抽象層與 CraftEngine 整合，讓本專案具備：

- 高擴充性
- 伺服器核心相容性
- 可配置的遊戲平衡
- 未來社群開發潛力

這正是 BreedingLog 之所以值得持續開發與維護的核心理由。
